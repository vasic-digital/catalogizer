## Why python3 and not Go

The task text names no language. docs/06 s13.7 says "a Go port if shell proves too slow, decided by measuring". A Go build must run in a build container through `scripts/containers` (11.4.173); `scripts/containers/run_pinned.sh` and `scripts/build/dispatch.sh` do not exist (only `probe_host.sh`, `disk_headroom.sh` are present), so a Go tool cannot be built here. The reference is python3 (stdlib plus the `jsonschema` package, 4.19.2 on this host) run on the bare host, which is an execution of a script, not a build. UNCONFIRMED: whether the owner accepts a python recorder as the shipped tool or wants the Go port; the interface is frozen by the two tests so a port can be checked against them.

## Interface decisions

- Canonical JSON: keys sorted, compact separators, UTF-8, `ensure_ascii` false (Python json). Ledger lines are written canonical; a verifier re-canonicalises each parsed line, so key order in a hand-edited file does not matter.
- `verify` exit codes (docs/06 s8): 0 verified, 1 chain failure (broken link, bad hash, non-contiguous seq, undecodable or torn line), 3 unverifiable (absent, unreadable or empty ledger). Exit 2 (anchor disagreement) is T055's. With no anchor compared, `verify` still exits 0 for a good chain and says on stdout `note: no anchor compared (T055); chain-only verification` (or `anchor ... present and NOT compared`). A chain-only 0 is therefore labelled, never presented as an anchored verification.
- `evrec` refusal codes, named on stderr as `reason=`: 64 usage_error, 65 record_invalid, 66 ledger_inconsistent, 67 schema_unavailable, 68 side_unverifiable / no_common_prefix / map_incomplete, 75 lock_held, 76 commit_turn_held (not a CPA exit code), 77 target_unreadable. A recorded command's own exit status is stored in the entry; `evrec run` exits 0 when it recorded.
- `target_fingerprint` is read from the target at run time (sha256 of the file bytes; a directory is a sha256 over sorted relative path and file hash). A target that does not resolve is refused (77) for RED, GREEN, MUTATION and REOPEN (no invented fingerprint); for the other polarities the entry carries sha256 of `UNRESOLVED:<ref>` because the ev/1 field is required and the entry cannot say otherwise (UNCONFIRMED: a schema field to mark an unresolved target would be a contracts change, not made here).
- `test_fingerprint`: sha256 over the lines of the hex digests of argv[0]'s resolved file and each `--test-source` / `EV_TEST_SOURCES` file, taken before the run. When argv[0] is an interpreter the sources must be declared (docs/06 s3.1 rule 11); omitted when argv[0] does not resolve, in which case the schema refuses RED/GREEN/MUTATION pass/fail entries.
- Optional `run` flags that carry the other ev/1 fields: `--oracle`, `--evidence-class`, `--precondition-provenance`, `--closes-item`, `--mutation-json`, `--container-image-digest`, `--pre-release`, `--test-state-go` (repeatable; the revision 6 field name stays UNCONFIRMED as in the contracts). Every entry is validated against `$FEAT/contracts/evidence-record.schema.json` BEFORE it is written; `schema_unavailable` (no jsonschema or no schema file) refuses, never writes unvalidated.
- stdout and stderr digests are those of the STORED (redacted) bytes, so the blob is addressed by its digest. Redaction: values of the variables named in `EVREC_REDACT_VARS` (shorter than 6 characters are skipped and reported, never silently half-redacted) are replaced by `[REDACTED:<NAME>]` in argv and both streams before anything is stored; the entry then carries `redacted: true`.
- Append: under a liveness-checked lock `<ledger>.lock` (JSON `{pid, cmdline}`); the inspect-reap-create step runs under an flock on `<ledger>.lock.guard` so two reapers cannot steal a lock a third just took. Stale = holder pid dead or its real `/proc/<pid>/cmdline` differs from the recorded one; an unreadable lock file is never reaped; a live holder is waited for `EVREC_LOCK_TIMEOUT` seconds (default 30) and then refused `lock_held`. The new ledger is written to a temp file in the same directory, fsynced, renamed, directory fsynced; `EVREC_FAULT=kill_before_rename` SIGKILLs the process between the temp write and the rename (test hook). Before appending, the last entry is checked for self-consistency and `seq == line count`; otherwise `ledger_inconsistent` (the full chain walk stays `verify`'s job).
- Commit-turn freeze: before running the command, writing a blob or appending, `.audit/commit_turn.json` under `EVREC_REPO_ROOT` (default: the repository of the tool) is read; a grant whose `run_id` is not `EVREC_TURN_RUN_ID` triggers at most one reaper call, only as `"${CPA_HOST_ENTRY:-$HOME/.local/bin/cpa-host}" --exec-approved scripts/release/commit_turn_check.sh --reap`; a failing or absent reaper leaves the grant standing; the grant is re-read and, if still held by another run, `commit_turn_held` and nothing is written. An unreadable or non-JSON grant is refused the same way without a reaper call. The append re-reads the grant inside the lock (no second reaper call).
- `rerecord`: both sides are chain-verified (or, with `--append-only`, only checked to be JSON lines), the common prefix is the count of byte-identical leading lines (none: refused), the output is the remote side byte for byte followed by the local entries after the prefix re-chained (new `seq`, `prev_hash`, `entry_hash`; every other field untouched), each re-chained record is validated against ev/1, and `ledger-seq-map.json` holds `[{old, new, digest}]` where `digest` is the new `entry_hash`. Nothing is written on refusal; output goes only under `--out`, written atomically. The output name `ledger.jsonl` follows T049's fixtures (an extra `--name` option exists for the deferral and flake ledgers). `remap-refs` rewrites every `ledger#<seq>` in the listed files in one regex pass (so 4 to 5 and 5 to 6 do not chain), and refuses, writing nothing, if any reference is not in the map.
- `verify` size report: the bound is read from `scripts/repo/check_classes.tsv` (`evidence-ledger` / `large_file`, 33554432), `EV_LEDGER_BOUND` overrides it for tests; `ledger_raise_owed` is named when the size is AT OR ABOVE 75% (T050 says "passes 75%"; the T049 fixture lands exactly on 75% when the size is divisible by 3, so `>=` is required). The flake ledger next to the ledger is measured the same way. The raise step itself is not implemented (held, reviewed, ST-QA's).

## Changes to the oracle test, with reasons (the test stayed the oracle; 54 checks, none removed, none weakened)

Both are fixture defects of `tools/evidence/tests/test_evrec.sh`, found by running the implementation against it:
1. The `CT_LOG` stub log is cumulative, so after the two refusal cases (which legitimately call the reaper) the check "matching run id never calls the stub" read a non-empty log. Fix: truncate `CT_LOG` immediately before the matching-run-id append. The assertion (a matching run id never calls the reaper) is unchanged and is mutation-tested (C4).
2. Under load, `sleep N & pid=$!; read /proc/$pid/cmdline` records the forked parent's command line before the child `exec`s, so the lock or grant holder looked like a cmdline-mismatch (reapable) holder and the live-holder cases failed intermittently when mutants ran in parallel. Fix: wait for the `/proc` cmdline to equal `sleep N ` before recording it (two places).
`test_evrec_more.sh` (23 checks) is new: it isolates each chain check (edited content, link only, reorder, non-contiguous seq, torn line, empty and absent ledger), the exit-status mapping, argv verbatim, blobs, RED entry acceptance and refusal, redaction in argv and stderr, a tampered side sharing a prefix in `rerecord`, and usage errors.
