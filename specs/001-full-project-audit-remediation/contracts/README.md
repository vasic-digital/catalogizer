Notes:

- `ev/1` adds `redacted`, `closes_item`, `container_image_digest` and a `MUTATION` polarity to the docs/06 §3.1 draft, and turns its prose rules 1, 4, 5 and 6 into schema conditions (research.md R-30). Revision 2 adds rule 10 of docs/06 §3.1 as conditions: `pass` <=> exit 0, `fail` <=> exit 1..125, new verdict `error` for 126, 127, 128+ and negative exits; RED never `pass`, GREEN always `pass`, a MUTATION entry is `fail` when caught and `pass` when it survived; RED, GREEN and MUTATION entries require `target_class` and `target_ref` (docs/06 §6) so the deriver can check "same test, different artifact".
- `finding/1` uses the docs/02 vocabulary (`S1..S5`, seven types); the register columns use the docs/04 vocabulary; the mapping is research.md R-12 and data-model.md §2. Revision 2: one canonical finding id `FND-NNNN` (register-minted) with the unit-local `F-<unit>-NNN` stored as `unit_alias`; `should_have_been_caught_by: none` requires `should_have_been_caught_by_justification`.
- Revision 2 validation script (scratch, not in the repository): `/tmp/schemacheck/check.py`, 21 samples, 0 mismatches, `jsonschema` 4.19.2 `Draft202012Validator` with `FormatChecker`.
- Revision 3 validation script (scratch, not in the repository): `.../scratchpad/schema/check_rev3.py`, 33 samples (21 `ev/1`, 12 `finding/1`), 0 mismatches, same validator. The justification pattern `^\s*(?:\S\s*){20,}$` alternates two disjoint classes, so it cannot backtrack exponentially (a 20,038-character failing string was refused in under 1 ms).
- `ev/1` revision 5 requires every `REOPEN` entry to be a genuine test failure: `verdict: fail` and `exit_status` 1..125 (a passing run, a harness error or a blocked probe observed no recurrence). The cross-entry part is the deriver's (docs/06 §4.2 step 7): a `REOPEN` cuts the fix cycle only when it is the same test as the cycle it ends and that cycle derived PASS; no GREEN of the new cycle may run on the `REOPEN` fingerprint or on an earlier-cycle GREEN fingerprint; and the deriver's `reopens_counted` must equal the register's reopen count for the item, which the outside verifier checks (SQL cannot read the ledger, docs/04 §7.2). Validation script (scratch): `.../scratchpad/r5/schema/check_rev5.py`, 40 samples (28 `ev/1`, 12 `finding/1`), 0 mismatches.
- `ev/1` revision 4 adds polarity `REOPEN` (the recorded recurrence of a closed item; requires `verdict`, `target_class`, `target_ref`; the deriver evaluates only entries after the item's last `REOPEN`, docs/06 §4.2 step 7) and defines `exit_status` of a `blocked` entry as the failing precondition probe's exit status, never 0 (the command was not run); the `blocked_reason` set is also the CHECK on docs/04 `reg_test_runs.blocked_reason`.
- `ev/1` revision 3 adds `test_fingerprint` (required on RED, GREEN and MUTATION entries whose verdict is `pass` or `fail`), requires `mutation` on every `MUTATION` entry, and adds `blocked_detail` and `counts_as` (both required with `verdict: blocked` and refused otherwise; docs/05 §10). Cross-entry rules are the verdict deriver's, not the schema's: one `test_fingerprint` across all RED and GREEN entries of a closure, every RED before every GREEN (max RED `seq` < min GREEN `seq`), and at least three distinct GREEN `iteration` values (docs/06 §4.2 step 7, executed in docs/06 §13.4).
- Importer checks for `finding/1` that JSON Schema cannot express (cross-field comparisons), refused by the register importer before any row is written: `fix.red_run` must differ from `fix.green_run`; both must name ledger entries of the same `test_fingerprint` and `target_ref` whose target fingerprints differ; `closure.evidence` must name a stored evidence blob. These checks are design, NOT EXECUTED (the importer does not exist yet).
- `bank-case/3` validates one case; a bank file is validated case by case. Rules R-3 to R-6 of docs/12 §6.6 need run results or cross-file data and stay in the validator script.
- How to re-run the validation: `quickstart.md` step 6.
