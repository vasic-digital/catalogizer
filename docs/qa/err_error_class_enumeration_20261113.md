## Instruments

Both are Go AST programs (go/parser, go/ast), built in a scratch directory; the sources are committed next to this doc as `docs/qa/err_error_class_scan/astscan_sinks.go.txt` and `all_error_calls.go.txt` (`.txt` so no Go tool picks them up). They were run on a clean clone at both bases, with each tree checked out without recursive submodule init.

1. **Sink scan.** For every non-test function it finds calls whose callee name looks like a response sink (names containing json, abortwith, string, write, send, respond, errorresponse, badrequest, servererror, encode, `http.Error`, html, data, emit, broadcast, notify, plus `c.Error`/`AbortWithError`); logger, `fmt.*`, `errors.*`, `strings.*` callees are excluded. An argument is reported when its subtree holds (E) a zero-argument `.Error()` call, (F) `fmt.Sprint*`/`Errorf` with an err-named identifier argument, (T) an identifier that the same function assigned from such an expression (taint, flow-insensitive), or (BARE) an err-named identifier passed as an argument.
2. **Census.** Every zero-argument `.Error()` call in every non-test file, with its syntactic context (argument of a named call, assignment, return, composite literal / key-value, branch, other). It catches flows instrument 1 cannot see (struct literals returned to a handler, helpers with unusual names).

## Class definition

A site is in the class when text derived from an `error` value can reach an HTTP, WebSocket or SSE response body or header, by any of these routes: (1) `err.Error()` or `%v/%w/%s` of an error inside a response call; (2) a bare error passed to a helper that serialises it; (3) error text stored in a struct or map that a handler later serialises; (4) error text kept in a variable and used in a response; (5) error text returned from a helper into a response. Sites that only log, branch on text, or record text in server-side state are outside the class and are counted separately in the census.

Classes used in the tables: **LEAK** (internal detail can reach the client: SQL/driver text, wrapped `%w` chains, paths, upstream or JWT parse text; "can include", not a demonstrated leak for every row: service and repository strings were read only where stated); **VALIDATION** (authored text that tells the caller which input to fix, or a sentinel's own text; may echo the caller's own input); **LATENT** (leaking code that no non-test caller can reach); **SAFE** (the err value does not reach the client: log-only, fixed-text helper, or a non-client sink); **CLOSED-BY-HELPER** and **CLOSED** are HEAD statuses, not classes.

### Classification rules (how the 20 old UNKNOWN rows were resolved)

Rule 1: a 4xx/5xx text produced by a service chain that contains `fmt.Errorf("...: %w", repoErr)` is LEAK (configuration GetWizardProgress, error_reporting GetErrorReport/GetCrashReport, auth Login/Refresh/ChangePassword via auth_service.go wraps, localization Import/Edit). Rule 2: text from a package-level sentinel or a `smartrules.ValidationError` is VALIDATION (playlist, service_handlers, conversion). Rule 3: `ErrLocalRootNotAllowed` text from `ResolveLocalRoot`/`CheckLocalRoot` is LEAK (it embeds `cannot resolve path: <OS error>`, local_policy.go:54). Rule 4: a binder (ShouldBindJSON) error on 400 is VALIDATION (mild: names Go struct fields). Rule 5: any other text on a 5xx or a variable status is LEAK.

## Limits of the instruments (measured, UNCONFIRMED where stated)

- No type information: any zero-argument `.Error()` matches, including non-error types (`writer.Error()` of encoding/csv appears in the census; read, not a response).
- Sink detection is by callee name; a response writer with a name outside the list is missed by instrument 1 and is caught only if instrument 2 sees an `.Error()` inside it. Error text built without `.Error()`, `%v` of an err-named identifier, or an err-named identifier argument (for instance a variable named `cause` or `e` passed to `fmt.Sprintf`) is not found by either instrument: UNCONFIRMED whether any exists.
- Taint is flow-insensitive within a function (one false positive found and read, user_handler.go:122 at HEAD). Taint through struct fields, other functions or channels is not followed; the census catches the `.Error()` call itself but not where the stored text is later sent.
- BARE reports any err-named identifier argument to a sink-named callee, including calls whose helper never serialises it (that is why 111 SendErrorResponse rows are listed as CLOSED-BY-HELPER rather than as leaks).
- Producers: service and repository error strings were read only where a row says so (auth_service.go, configuration_service.go, error_reporting_service.go, local_policy.go, localization_service.go, playlist_service.go). Every other LEAK means "text can include internal detail", not a demonstrated leak.
- Not covered: Go modules other than catalog-api and OCU-CUDA-Sidecar (examples/, docs/qa/lib/ctrctl, catalog-api/tests/automation, tools/ fixtures were not scanned), JavaScript/TypeScript backends, generated code, and HTTP responses produced by third-party middleware. WebSocket (`handlers/websocket_handler.go`) and SSE (`log_management_handler.go`) code was grepped: error values there go to `h.logger` only (UNCONFIRMED beyond that grep).
- HEAD status was produced by matching each review-base row to the HEAD scan by (file, function, sink, kind, expression) and then reading the helper and the changed line for the rows that moved; line numbers shift, so the match ignores them.
