## Purpose

Fails when a compose file, a Dockerfile or Containerfile, or a shell script references an external image without a full
`@sha256:<64 lowercase hex>` digest, or installs software by piping a download into a shell. docs/16 section 7.1 step 3 and findings D-05
and D-07 name it; docs/20 W20-01 and W20-02 need it to reject mutable tags and `curl | sh`.

## Usage

```bash
scripts/containers/check_pins.sh [--root DIR] [--list] [--recurse] [--exclude-dir NAME]... [PATH...]
```

| Option | Meaning |
|---|---|
| `--root DIR` | root the reported paths are relative to (default: git top level of the cwd, else the cwd) |
| `PATH...` | files or directories under the root to scan; default every tracked file (`git ls-files`) or, outside git, every file |
| `--recurse` | with the default file set, also the files of every submodule checkout |
| `--list` | one TSV row per violation, `rule`, `path`, `line`, `reference`, no summary (the baseline form) |
| `--exclude-dir NAME` | skip directories of this name (`.git`, `node_modules`, `vendor`, `.audit` are always skipped) |
| `--dump-engine-options` | print `table<TAB>option` for every value option of the three tables (run, pull, global) and exit 0: the comparison input of the table-equals-snapshot check |

Output: `VIOLATION <rule> <path>:<line>: <reference or excerpt>` per finding, sorted by path, line, rule, then
`check_pins: N violations in M files scanned`. Exit 0 clean, 1 violations, 2 usage, **3 internal error** (an uncaught exception: nothing is printed on stdout, a traceback and
`check_pins: internal error: ...` go to stderr; an input file that cannot be read is also exit 3: `check_pins: cannot read <path>: <reason>`, never "0 violations", WF13 N7). A caller that compares rows with a baseline must treat 3 as a failure of the check, never as zero rows (WF10 p1 F3).

## Rules

| Rule | Fires on |
|---|---|
| `compose_image_unpinned` | `image:` in a compose file (name contains `compose`, `.yml`/`.yaml`) without a full digest; the value may be on the next line; `${VAR:-default}` is judged by its default; a bare `${VAR}` or `$VAR` and `localhost/` images are not judged. A service that also has a `build:` key names the tag its build produces, but compose pulls first unless `pull_policy` says otherwise (compose spec, build.md): it is local, and skipped, only with `pull_policy: never` or `build`, or when the name is a single component (no namespace, no registry host) and no `pull_policy` is given. A namespaced or registry-qualified name (`someorg/tool`, `ghcr.io/o/x`, `registry:5000/tool`), or any other policy (`always`, `missing`, `if_not_present`, `daily`, `weekly`, `every_<duration>`, a variable) is pulled from a registry and judged. The `pull_policy:` is read from the same service only |
| `from_unpinned` | `FROM` of a Dockerfile/Containerfile with an external image without a full digest (build-stage aliases, `scratch`, `localhost/` skipped) |
| `from_arg_unpinned` | `FROM ${ARG}` / `${ARG:-default}` whose default exists and has no digest (an `ARG` without a default is the builder's input). Only `ARG` lines before the first `FROM` are global; a stage-local `ARG X` after a `FROM` neither hides nor replaces the global default; several `NAME=value` on one `ARG` line are all read |
| `copy_from_unpinned` | `COPY --from=` / `ADD --from=` / `RUN --mount=...,from=` naming an external image without a digest (a stage alias, a stage number, `localhost/` or a `$` value is not judged) |
| `script_image_unpinned` | the image operand of `docker\|podman\|nerdctl run\|pull\|create` (also `buildah from\|pull`), including a bare name (implicit `:latest`). The engine word is looked for at ANY position of a simple command (so `$SUDO podman run`, `timeout -s KILL 30 podman run`, `retry 3 podman pull`, `ssh host podman run`, `eval podman run`, `env -u FOO podman run`, `sudo --user root podman run` are all seen), except in a command that only talks about commands (`echo`, `printf`, `grep`, `sed`, `awk`, `tee`, `man`, `which`, `type`, ...); an engine kept in a variable (`$DOCKER`, `${PODMAN}`, `${CONTAINER_ENGINE:-podman}`, `$ENGINE`, ...) is recognised by name. Looked through: `&&`, `;`, `\|`, `$(...)`, quoted `"$(...)"`, `sh -c '...'` / `ssh host "..."` / `eval` strings (engine at any position), a quoted command line handed to an unknown helper (only when it STARTS with the engine and the operand looks like an image reference), global options (`podman --log-level error run`) and `image`/`container`. Plus any registry-qualified reference with a tag in a `.sh`/`.bash` file, also inside `${VAR:-ref}` / `${VAR=ref}` / `${VAR-ref}` / `${VAR:=ref}` (a `docker://` prefix is removed first). An operand `${VAR:-default}` is judged by its default; `localhost/` and `$VAR` operands are not judged. Option values are skipped by the per-verb tables generated from the engine help (below); an unknown option is a boolean, except that a following `key=value`, port, address, `host:ip` or `host:host-gateway` token is its value |
| `pipe_to_shell` | a pipeline whose stages include a download (`curl\|wget\|fetch`, at any earlier stage, inside a piped group/subshell or for-loop, or in an install hint printed by `echo`/`log`) and whose later stage READS A PROGRAM from its stdin: a shell (`sh bash zsh dash ash ksh mksh csh tcsh fish rbash`, any arguments, also by path, also behind `sudo/doas [options]`, `env [-i -u X VAR=x]`, `nice -n`, `busybox`, ...), or an interpreter (`python* perl ruby node nodejs php lua deno bun Rscript`) with no script operand and no inline-code flag (`python3`, `python3 -`, `perl`, `node`: stdin is the program; `python3 -m x`, `-c`, `-e`, `-p`, `-r`, a script file: not). `\|` and `\|&` join stages; `&&`, `\|\|`, `;` do not. Also `bash <(curl ...)`, `bash < <(curl ...)`, `source <(curl ...)`, `. <(curl ...)`, and `sh\|bash\|eval\|python*\|perl\|ruby\|node\|php [options] "$(curl ...)"` / backticks; in a Dockerfile/Containerfile or script. A pipe continued onto the next line by a trailing `\|`/`&&`/`\|\|` or a backslash, and a for-loop of downloads spread over lines, are one logical line reported at its first physical line; a quoted install hint a script prints is flagged too. `\| python3 -m json.tool`, `\| python3 -c`, `\| perl -ne`, `\| node -e`, `\| ruby script.rb`, `\| tee sh`, `\| grep bash`, `\| sha256sum`, `\| ssh host cat` are not shell installs |

Carriers do not fire (11.4.201): `#` comments (full-line and trailing) are removed first; Markdown, text and every other file type are not scanned.
In a script under a `tests` directory (and ONLY there: a `test_*`/`mutate_*`-named script elsewhere is operational code, WF13 N8; the three such files under `specs/.../evidence/wp05/T050r3-baseline/` produce no row either way, measured) the here-document bodies are fixture data and are not judged (a `<<` inside a quoted string, a here-string `<<<`, or arithmetic `$((a<<b))` / `(( a<<b ))` with any nesting of parentheses does not open one), the simple commands that only write or filter data (`printf`, `echo`, `sed`, `tee`, `grep`, `awk`, a bare `VAR=value` without a `$(...)`) are masked for the pipe and run rules, quoted strings handed to a helper (single-quoted, and double-quoted without a command substitution) are fixture data, and a registry-qualified literal outside a real engine command is not judged; a real `docker|podman run|pull|create` at the top level of a test script, or inside `"$(...)"`, is still judged. In any other script they are judged like code. A UTF-8 byte-order mark before the first line is ignored.

## Honest limits

- The scan reads text. It does not resolve a registry, does not expand variables other than a `${VAR:-default}` default, and does not prove that a
  digest exists or is signed (signature verification is T149's `IMG-SIGVERIFY`).
- Script image detection is a heuristic: the operand after the option list of `docker|podman run|pull|create`, and registry-qualified references with a
  tag. An image named only through a variable or a config file is not seen. A `FROM` line inside a script's here-document is not a `FROM` of a Dockerfile.
- Not resolved by the scan: a script without a `.sh`/`.bash` extension (the repository has 4 extensionless shell scripts, none with an engine or pipe use, measured), a `Makefile` command (the main repository tracks none), an image named only through a variable or a config file, an engine in a variable whose name is not in the recognised list, a value option unknown to the tables whose value looks like an image (the tables are the podman 5.7.0 help plus the docker reference; `nerdctl` and `buildah` options are UNCONFIRMED, those tools are not installed), a registry host outside the closed list of the registry-literal rule (`index.docker.io`, `k8s.gcr.io`, `nvcr.io` are seen only as an engine operand).
- The mutation `strip-line-comment` (skipping the full-line comment branch of the line joiner) is equivalent: `strip_comment` removes the same lines, so
  it is not in the table (UNCONFIRMED that no further equivalent mutants exist).
- Baseline: the first main repository measure (91 rows at HEAD 7f5e9f4b plus uncommitted work, it contained the false positives removed since; its header cites a `t105-notes.md` that was never written) is `evidence/wp11/pins-baseline.txt` and is SUPERSEDED by `evidence/wp11/wf13fix-p1-pins-after.tsv` (the live rows of this revision: 52); the recursive measure over
  every submodule checkout is `evidence/wp11/pins-baseline-recursive.txt` and includes third-party submodules (the own-organisation filter is the
  CPA's, T040 rule W, UNCONFIRMED). The plan review's 45 compose lines plus 6 deploy lines were not reconciled row by row with the rows measured here.
- Mutation table labels: the R-rows are R1-R12 plus R2b (13 rows); the N-row numbers are labels, not a sequence: N02, N12, N27, N30, N34, N35, N37-N39, N45 never appeared in the committed table (UNCONFIRMED why).
