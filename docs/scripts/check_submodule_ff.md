## Purpose

A local gate that FAILs when a commit range moves an own-org submodule gitlink NON-fast-forward: the new pin is not a descendant of the old pin (`git merge-base --is-ancestor OLD NEW` fails), so the move went backward or sideways and drops submodule commits from every clone of the parent (constitution 11.4.113, 11.4.288(D), 11.4.233(G)). It reads only; it never fetches, commits or pushes. Side effects on the scanned repository: none (refs, objects and index unchanged; the control needle builds its own throwaway repository under `mktemp -d`).

## Usage

`scripts/check_submodule_ff.sh OLD NEW`, `scripts/check_submodule_ff.sh OLD..NEW` (run inside the parent work tree), or `scripts/check_submodule_ff.sh --selftest` (control needle only). Env `SUBFF_OWN_ORGS=<file>` replaces the own-org list (default `scripts/audit/own_orgs.txt`); its first entry is the organisation of the control needle's URL. Example before a push: `scripts/check_submodule_ff.sh origin/main HEAD`.

A symmetric range `OLD...NEW` is rejected (exit 64, `ERROR symmetric range A...B is not supported; use OLD..NEW or OLD NEW`). A work tree is required: bare repositories and server-side `pre-receive` hooks are not supported. A shallow parent repository gives `VERDICT: BLIND reason=parent-shallow` (exit 2), because its history ends at the shallow boundary. Cost, measured 2026-10-29 on the Catalogizer tree (read-only): `HEAD~30..HEAD` is 96 commits including merges, 12 gitlink moves, 10.1 s, so about 0.1 s per commit; earlier rounds measured up to about 0.25 s per commit on smaller fixtures. A long range takes seconds to minutes.

It compares every commit of `OLD..NEW` with EVERY one of its parents (so a merge that keeps the local pin and drops the other parent's advance is seen), and also the `OLD` tree with the `NEW` tree (lines tagged `commit=RANGE`). Commits are walked parents-first (`rev-list --topo-order --reverse`). A pin moved backward in one commit FAILs on that commit even when a later commit moves it forward again, because each per-commit diff is classified on its own; the `RANGE` line alone would see only the net change.

Remove and re-add across commits: every gitlink a per-commit diff removes (and does not pair as a rename in that same diff) is remembered with its last pin, its `.gitmodules` name and its canonical URL key. Removals are remembered per line of descent: commits are walked parents first (`rev-list --topo-order --reverse`), each commit starts from the union of the removals remembered by its parents, and a removal is visible only to the commits that descend from the commit that made it. So a re-add on one branch is never compared with a removal made only on a parallel branch, and the order of the walk (committer dates) cannot hide a removal from its descendants. When a commit adds a gitlink that its own diff cannot pair, the gate looks for remembered removals on its line with the same non-empty `.gitmodules` name, whatever their URLs: a URL key that differs does not prove another repository (a relative `../sub.git` or a mirror host is not collapsed to the same key), so the name decides. Name matches are the same submodule, so every distinct remembered pin is compared (parallel branches may have removed it at different pins: FF from all of them PASSes, NONFF from any FAILs) and all are consumed. Only if there is no name match, removals with the same non-empty URL key are used: one pin is compared, and different pins give `BLIND <class> ?=><newpath> - <newpin> commit=<sha> reason=readd-ambiguous` (exit 2). A URL-key match consumes the key matches but keeps each removal whose name differs from the added name available for a later re-add under that name, so a same-URL sibling added in between cannot hide a re-add at an older pin. Only if there is neither a name nor a URL-key match, removals at the same path are used: every distinct pin is compared and all are consumed. When the removal or the addition has no `.gitmodules` name (a gitlink without a `.gitmodules` entry, or a section removed one commit before its gitlink) the path alone decides. When both have names (they differ) the removal is taken if one local store holds both pins (shared history: the same repository renamed, compared FF or NONFF) or if no store resolves either pin (nothing can be told: compared, BLIND); it is left alone, and the addition reported `ADDED`, only if a store resolves one of the pins but none holds both (another repository at that path). If still nothing matches and the addition is own, a remembered removal with neither a name nor a URL key can never be identified: the addition is `BLIND own ?=><newpath> - <newpin> commit=<sha> reason=readd-unidentified` (exit 2) and that removal is consumed. A third-party addition leaves such removals alone. A hit is checked as a move `<oldpath>=><newpath> <removedpin> <addedpin>` (FF, NONFF or BLIND, exactly like an in-place move), so a chain of renames `sub` -> `lib` -> `tool` is compared hop by hop, and the added gitlink is not printed as `ADDED`. The removal itself is still printed as `REMOVED` in the commit that removed it. The `OLD` -> `NEW` diff (lines tagged `commit=RANGE`) never uses remembered removals; it compares only the endpoints.

Renames: a gitlink deleted at one path and added at another in the same diff is checked as one move `old=>new` when both sides have the same `.gitmodules` name, or, when the name changed too, the same canonical URL. Canonical form: the scheme form (`ssh`, `git`, `http`, `https`, `git+ssh`, `ssh+git` `://[user@]host[:port]/path`) and the scp form (`[user@]host:path`, accepted only with a user or a dot in the host, so `localbox:vendor/sub.git` is a local path) both reduce to `host/path`, lowercased, with `.git` and trailing `/` removed; user and port are dropped; for scheme URLs any `?query` and `#fragment` are removed first. A path containing `~` or `%` (for example `~user/repo` or a `%2D` escape) is kept literal and never counts as a remote, so it is own. The same key decides own-org matching (its organisation is the first of exactly two path segments). If one commit removes an own-class gitlink and adds an own-class gitlink that cannot be paired, the removal is `BLIND own <oldpath>=>? <oldpin> - commit=<sha> reason=unpaired-rename` (exit 2): it may be a rename whose name and URL both changed. URL pairing is used only when it is unambiguous: if two removals, or two additions, in one diff share one URL key, every such removal is `BLIND <class> <oldpath>=>? <oldpin> - commit=<tag> reason=ambiguous-pairing` (exit 2) instead of being paired by first match (a swap of two submodules with the same URL would otherwise pair wrongly). Other unpaired leftovers are reported as `REMOVED` / `ADDED`.

Submodule ignore settings: every diff runs with `--ignore-submodules=none`, so `submodule.<name>.ignore=all` (in the repository config or in `.gitmodules`) and `diff.ignoreSubmodules` cannot hide a move. As an independent check the gate also lists the `OLD` and `NEW` trees with `git ls-tree` (which no ignore setting affects) and counts the gitlink paths whose entry differs; that count must equal the number of gitlink entries the `RANGE` diff saw, otherwise `VERDICT: BLIND reason=gitlink-diff-mismatch` (exit 2). An `ls-tree` failure is `reason=git-error`. So `note=nothing-checked` can only come from a range in which the trees really have no differing gitlink.

Counters count reported lines, not distinct moves: the same move is usually reported once per commit and once as `commit=RANGE`, so `checked` and the per-class counts double-count. Read them as "something was seen", not as a move count. An empty range, or a range with no gitlink change, prints `checked=0 ... note=nothing-checked` and exits 0: nothing was checked, which is not the same as a verified clean range.

Output lines:

- `FF|NONFF|BLIND <own|third-party> <path> <oldpin> <newpin> commit=<sha> [reason=...]`
- `ADDED|REMOVED <own|third-party> <path> <pin> commit=<sha>` (reported, never failed)
- `BLIND own <oldpath>=>? <oldpin> - commit=<sha> reason=unpaired-rename`
- `BLIND <own|third-party> <oldpath>=>? <oldpin> - commit=<sha|RANGE> reason=ambiguous-pairing`
- `BLIND <own|third-party> ?=><newpath> - <newpin> commit=<sha> reason=readd-ambiguous`
- `ERROR .gitmodules of <commit> cannot be parsed (git config exit <n>)`
- `NEEDLE forward=FF backward=NONFF class=own` then `NEEDLE ok`
- `VERDICT: PASS|FAIL|BLIND checked=N own_ff=N own_nonff=N own_blind=N third_party_ff=N third_party_nonff=N third_party_blind=N [note=nothing-checked]`

Exit: 0 PASS; 1 FAIL (an own-org NONFF, wins over BLIND); 2 BLIND (an own-org pin not found in any local object store of the submodule, a shallow store, a store with `info/grafts`, an ancestry query error, any `git rev-list` or `git diff-tree` error (`reason=git-error`), a parent repository with `info/grafts` (`reason=parent-grafts`), a shallow parent (`reason=parent-shallow`), an unpaired own remove plus add (`reason=unpaired-rename`), an ambiguous same-URL pairing (`reason=ambiguous-pairing`), an ambiguous re-add of an earlier removal (`reason=readd-ambiguous`), a `.gitmodules` in any scanned tree that `git config` cannot parse (`reason=gitmodules-unparsable`: a URL the gate cannot read could be the own one, so it is never ignored; because `git config --get-regexp` exits 1 both for "no matching key" and for a malformed file, each `.gitmodules` is first parsed with `git config --blob <commit>:.gitmodules --list`, which exits 0 on any well-formed file, an empty one included), an `ls-tree` count that disagrees with the `RANGE` diff (`reason=gitlink-diff-mismatch`), an own-org list that matches no URL in the range while some move was classed third-party (`reason=own-orgs-match-nothing`), a failed control needle, or `python3` / `scripts/audit/org_of.py` missing); 64 usage error (no arguments, `OLD...NEW`, unknown ref, not in a work tree, unreadable or empty own-org list, or an inherited `GIT_DIR` / `GIT_WORK_TREE` pair that does not name one repository).

## Environment

The gate first records the repository the caller is in (`git rev-parse --show-toplevel` and `--absolute-git-dir`, honouring whatever the caller exported), then unsets `GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE`, `GIT_OBJECT_DIRECTORY`, `GIT_ALTERNATE_OBJECT_DIRECTORIES`, `GIT_COMMON_DIR`, `GIT_NAMESPACE`, `GIT_GRAFT_FILE` and `GIT_PREFIX`, and re-resolves the repository from the recorded top level. If the re-resolved git dir differs from the recorded one it exits 64. Every later call uses explicit `-C` / `--git-dir`, so inherited variables (for example from a `git -c alias.x='!...'` call inside a linked worktree) can no longer point the control needle or the scan at the wrong repository. It exports `GIT_NO_REPLACE_OBJECTS=1` (replace refs and `replace --graft` cannot fake ancestry), `GIT_NO_LAZY_FETCH=1` (a partial clone never fetches), `GIT_TERMINAL_PROMPT=0` and `GIT_OPTIONAL_LOCKS=0`.

## Classification

The `.gitmodules` file is parsed at every tree the scan touches (`OLD`, `NEW`, every commit of the range and every parent). A gitlink is own-org if its name or path has an own-org URL ANYWHERE in the range, else third-party if it has a third-party URL anywhere, else own-org. So switching the URL to a third-party one for one commit, or only at one end, does not hide a backward move.

A URL is third-party only when its canonical form (see Usage) is a remote with exactly two path segments and its organisation, parsed by `scripts/audit/org_of.py` and lowercased, is not in the own-org list. Everything else counts as own-org (fail closed): local or relative paths, `file://`, an IPv6 host such as `ssh://[::1]/org/repo`, a `git+https://` or other unlisted scheme, a path with `~` or `%`, a URL with one or three path segments, or no `.gitmodules` entry. Relative URLs (`../sub.git`) are deliberately NOT resolved against the parent's `origin`, because `origin` may be a personal fork whose organisation is not the project's; they are always own, so a backward move of a relatively addressed submodule FAILs. The own-org list is compared case-insensitively; blank lines and `#` comments (whole-line or inline) are ignored. Third-party moves are printed with `third-party` and counted in the `third_party_*` fields; they never change the exit status, including a third-party BLIND.

Stale-list guard: if the range checked at least one gitlink move, at least one move was classed third-party, and the own-org list matched NO URL seen in the range (moved or listed in any scanned `.gitmodules`), the verdict is `BLIND reason=own-orgs-match-nothing` (exit 2), so a list from another project cannot quietly turn every move third-party and PASS. Moves that are own anyway (relative or local URLs, no `.gitmodules` entry) cannot be hidden by a wrong list, so a range with only such moves is decided normally. Consequence: a repository whose submodules are all third-party is always BLIND when pins move; give it an own-org list that names one of its organisations or do not run the gate there.

Limit of the guard: it catches a list that matches nothing, not a list that is only partly stale. If the list still matches one own submodule but has lost the organisation of another, that other submodule is classed third-party and its backward move passes (reported as `NONFF third-party`). Keep the list complete; review `third-party` lines in the output.

## Object resolution and BLIND

Both pins must be present in `<git-common-dir>/modules/<name>` or in the checked-out `<path>/.git`. If neither does (typically after a submodule rename, when the store still sits under the old name and the checkout is gone), the gate falls back to every store under `<git-common-dir>/modules/**` in sorted order and uses the first one that is not shallow, has no `info/grafts` and holds BOTH pins; a shallow or grafted store is skipped there rather than reported. Every git call on a store passes `--work-tree=<store>`: a store left behind by a rename keeps `core.worktree` pointing at a checkout that no longer exists, and git would otherwise exit 128 (`cannot chdir`) on every command, which is how the false `pin-not-in-local-object-store` arose. If no store holds both commits the entry is `BLIND ... reason=pin-not-in-local-object-store`. A shallow store gives `reason=shallow-store` and a store with `info/grafts` gives `reason=grafts`: neither can decide ancestry honestly. An ancestry query that errors (for example a missing intermediate commit) gives `reason=merge-base-rc-<n>`. The gate never fetches. Run `git submodule update --init` (or a fetch inside the submodule) first when you need a verdict on a fresh clone. BLIND is never reported as PASS (11.4.201, 11.4.273).

## Control needle

Every run first builds a throwaway repository under a `mktemp -d` directory with one known forward and one known backward gitlink move of a submodule whose URL is `git@github.com:<first own org>/needle_sub.git`, and passes it through the same scan function (its commits run with `-c core.hooksPath=/dev/null -c commit.gpgsign=false`, so no user hook or signing runs). It requires `FF own` on line 1, `NONFF own` on line 2 and its own marker `ORGMATCH 1` on line 3 (the own-org list really matched the needle URL; any extra or missing scan line moves the marker off line 3). Otherwise the gate prints `VERDICT: BLIND reason=control-needle-failed` and exits 2. So a broken org parser or a first list entry that cannot form an org URL (for example `bad/org`) blinds the gate.

Equivalence notes (mutants without a dedicated killing fixture, with the reason):

- OM8 (`= true` instead of `!= false` in the shallow-store check): `git rev-parse --is-shallow-repository` prints only `true` or `false`. The two forms differ only when that command fails on a store that `cat-file -e` read successfully a moment earlier, which only a race can produce. `!= false` is kept because it fails closed.
- OM2 (classify a rename by the new URL only) and the earlier side-only classification mutants are subsumed by range-wide classification; their fixtures stay.
- C1_needle_any_class (accept any class in the needle): the needle repository has exactly one URL, so the needle can be classed `own` without the own-org list matching only through the unparsable-URL fallback, and that case already fails the `ORGMATCH 1` line-3 check. The class check is equivalent to it; the mutant is listed in the test file as a comment and not run.
- OM3 (pair entries with empty URLs): as originally written (drop only the `-n ad_key` test in the pairing line) it became equivalent in round 5, because the URL pass is entered only for a removal with a non-empty key, so an empty `ad_key` can never equal it. It was retargeted to remove every empty-key guard (the loop-top `-n rm_key` and both `-n ad_key` tests) and is killed by the unnamed remove+add fixture.
- OM4 (prefix match on the path): the lookup is an exact associative-array key `commit<TAB>path`, so a prefix match cannot happen; the fixture stays as a guard.

## Honest limits

- Not wired into any hook or pipeline yet; it is run by hand or from a release or push procedure.
- No fetch: a pin missing locally is BLIND, not resolved. A fresh clone needs `git submodule update --init` first.
- A partly stale own-org list classes the lost organisation third-party (see Classification); only a list that matches nothing is caught.
- A submodule whose URL was switched to a third-party fork in the range stays own only if its name or path has an own URL in some tree of the range; a rename to a new name and a fork URL at once is BLIND (`unpaired-rename`) or, with a third-party side, REMOVED plus ADDED.
- Relative URLs are never resolved, IPv6, `git+` and `file://` URLs are never treated as remotes: all are own (fail closed).
- The store fallback picks the first sorted store that holds both pins; two unrelated stores holding the same commits would give the same ancestry answer, so the pick does not change the verdict.
- A rename whose name AND URL both change is BLIND (`unpaired-rename`) when both sides are own; with a third-party side it is reported as REMOVED plus ADDED (no pin comparison).
- A repository with only third-party submodules is always BLIND when pins move (stale-list guard).
- Bare repositories and `pre-receive` hooks are unsupported (a work tree is required).
- Counters double-count (see Usage); `note=nothing-checked` marks a run that checked nothing.
- Third-party BLIND does not affect the exit status.
- Remembered removals follow the line of descent only. A re-add on a branch parallel to the removal is checked only by the per-commit diffs and the `OLD` -> `NEW` diff: if the merge keeps the removal side (`-s ours`) the added pin is never compared with the removed one (the submodule is absent at `NEW`, so no clone gets the older pin).
- Same name, any URL: an addition with the name of a remembered removal is always compared with it. The gate cannot tell a different repository reusing the name from the same repository under another URL form, so it does not try: a different repository normally gives BLIND (`pin-not-in-local-object-store`, no store holds both pins), and it can give NONFF only if one store holds commits of both (shared history). It never gives ADDED or a silent PASS. To clear such a BLIND, check a range that starts after the reuse.
- Path matching is used only after name and URL-key matching found nothing. A removal at a path later reused under another name is compared when one local store holds both pins or when no store resolves either pin; if a store resolves one pin and none holds both, the addition is reported `ADDED` and not compared. That last case can hide a backward move only if the clone holds the objects of one pin and not the other, for example a store fetched before the older pin existed upstream; the gate reports the pins in the `ADDED` and `REMOVED` lines so a reader can check. A removal without a name re-added at the same path is compared even if it is another repository (BLIND or NONFF, never a silent PASS).
- `readd-unidentified` is fail closed and can be a false BLIND: a removal with neither a name nor a URL key consumes the first own addition after it on its line, even an unrelated one. Each such removal gives at most one BLIND.
- `readd-ambiguous` is BLIND, never resolved: when several same-URL removals with different pins match an addition by URL only, the gate does not guess which copy came back.
- Removals made before `OLD` are not tracked: a submodule removed before `OLD` and re-added inside the range is `ADDED` (no pin to compare), so pick `OLD` before the removal to check such a re-add.
- Several git calls per commit and per gitlink change: about 0.1 to 0.25 s per commit measured.
